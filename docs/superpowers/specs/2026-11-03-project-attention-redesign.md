## 0. 为什么重做

下面是一个真实 Project（「接入 Super-agent 到鲸鱼娘个人助理」，一周，34 轮协调者回合，9 条工作）的记录。只有这一个样本，只用来说明问题的形状，不当统计。

| 观察 | 数字 / 事实 |
| --- | --- |
| 协调者的回合多数不是用户触发的 | 34 轮里，用户说话触发 15 轮；成员完成通知触发 16 轮；队列激活通知触发 3 轮。系统触发的 19 轮产出了协调者约 74% 的文字（约 1 万字符，平均每轮约 530 字） |
| 每次恢复前都要读一大份 `notes.md` | 提示词要求「恢复工作或汇总前读 `notes.md`」。57 次读取，平均约 2 万字符，最大约 5 万，累计约 113 万字符。大头是**历史交付的完整正文**：每次返回最近 10 条交付的全文，平均约 1.6 万字符，后期恒定约 2.8 万；用户笔记当时是空的 |
| 派了做不到的工作 | 用户让它调研一个 GitHub 链接。协调者把它派给只读成员，而没有任何一个范围能读网页。成员做了 95 次本地读取、48 次本地搜索，三次如实报告 `blocked`（缺网页取文能力）。协调者约半小时后承认「这一步安排不合适」，并如实告诉了用户；但那时调研已经做不成，之后的接入方案也只能把 pstack 部分标为「待核实」 |
| 一次瞬时故障让流水线停在半路 | 协调者在汇总时遇到服务商过载，当轮失败、不重试，停在「成员已完成、未汇总」（Harness 侧已由 #345 修复） |
| 看不出进度 | 用户需要问「啥进度了」 |

这些问题不是「界面不好看」，是**协调者与成员的行为、停下的条件和状态的表达**出了问题。

## 1. 准绳

dsh-superagent 的第一条原则：**占用尽可能少的人的注意力，给出尽可能多的价值。** 一条消息、一个通知、一个问题、一个设置、一个面板元素，每一个都要比它占用的注意力给出更多价值，否则删掉。

4.2 的准绳是「更好用」。两者不冲突，5.0 把「好用」具体化为注意力预算：

1. **只在你必须行动或能用上结果时才说话。** 其余时间安静，进度由面板显示，不由对话叙述。
2. **一次只问一个具体的问题**，用结构化的方式问，而不是埋在一大段回复里。
3. **按影响停下，不按工作量停下。** 拿不到必要输入、权限或工具，就停下并说清缺什么，不把没拿到的当成拿到。
4. **如实汇报。** 草稿标未完成，失败写失败，限制不绕过。
5. **面板只展示需要你的事。** 一切正常的状态不占位。

## 3. 设计

### 3.1 阶段：一个需求同一时刻只有一个，写明等谁

自上而下，**首个匹配的行生效**，类别互斥且覆盖所有情况。标签写「谁在等、需要什么」，不写内部状态码。

| 阶段 | 条件 | 标签 | 等谁 |
| --- | --- | --- | --- |
| 等你回答 | 有未回答的提问（§3.2） | 等你回答：〈问题〉 | 你 |
| 等你决定 | 部分交付；或汇总 / 交付失败且自动重试用尽 | 部分交付，等你决定 · 汇总未完成，可重试 | 你 |
| 受阻 | 成员报告 `blocked` / `failed`（含拿不到输入），且之后没有你的消息 | 受阻：〈缺什么〉 | 你 |
| 排队中 | 等前一条需求、依赖、目录或容量 | 排队 · 第 N 位 / 等〈谁〉 | 系统 |
| 进行中 | 其余 | 进行中 | 系统 |
| 讨论中 | 未授权 | 讨论中 | 你（决定是否开始） |

终态：已交付、已取消、已归档。头部徽标和面板顶部的数字 = 前三行之和，**等于它链接到的列表的长度**。

状态仍是现有数据的派生视图（4.2 §3.3），只新增「未回答的提问」这一个持久化事实。

### 3.2 提问：一个具体的问题，结构化

- 协调者新增 `project_ask`；成员的 `project_report` 增加 `humanAction`（一个具体问题）。
- 结构：问题（一句）、可选的选项、「你不回答时会发生什么」（比如「我会先做 X，Y 等你」）。
- 每个需求最多一个未决提问；重复同一问题复用，不同问题替换；回答或清除必须显式，后续进展不算回答。
- 你的下一条消息即视为回答；协调者继续，不再问「要继续吗」。
- 展示：面板「需要你」置顶、头部徽标、对话里**一条**短消息（只发一次）。原生的命令审批并入同一列表展示，审批本身仍走原生机制。
- 已授权范围内无歧义的工作可以在等待期间继续。

### 3.3 停下的三种情况

4.2 的规则 2 是「默认往前跑，只在真正的岔路口停」，只列了两类：不可逆或对外的动作、无法判定的抉择。5.0 补第三类：

> **(c) 必要的输入、权限或工具拿不到。**

真实记录里，成员做得对（三次如实报告 `blocked`），问题出在**派工之前**：协调者不知道所有范围都读不了网页，就把调研链接派了出去，白白耗掉约半小时。所以 (c) 的重点是派工前核对，其次才是出错后的处理。

规则：

- **派工前先核对**：这一阶段需要的输入、权限、工具，现有范围都提供吗？不提供就先告诉用户，要材料或要一个决定，**不派工**，不靠「让成员自己想办法」。研究范围（§3.9）落地后，读网页属于它提供的能力。
- 已经派出的工作报告 `blocked` 时：协调者说清缺什么、已经试过什么、最小需要你做的动作。依赖它的阶段不派发。
- **不得把没拿到的输入当成已满足**。用户回复后只有两种继续方式：给出了替代输入，或明确说「就用现有材料」。
- `blocked` 只在人必须行动时使用，不因为「还有半成品」而用。
- 「工作量大」不是停下的理由；「需要破坏现有调用方、或要协调多个独立模块的重新设计」才是（沿用 dsh-superagent 的范围规则）。
- 不新增报告状态 `dropped`：dsh-superagent 里它表示「没有人需要做的事」，Project 的需求都由用户提出，总有结果要交付，`blocked`、`failed`、`completed` 已经够用。

### 3.4 对话只说三种话

1. **确认一次**：「已记为需求：X」，并说明会做什么、做完是什么样。
2. **交付、提问、无法完成**：一句话，默认不超过 100 词；不含库名、文件路径、提交号、测试数量，这些放在交付页里。
3. **直接回答你的问题**。

由**成员完成通知或队列激活通知**触发的回合，默认**不产出给你的文字**：只更新 todo、派发下一阶段。只有当这一轮本身就是交付、提问或无法完成时才说话。进度由面板显示。

这些通知在对话里应折叠成一行（「〈成员〉完成了〈工作〉」），而不是原始内容。现在它们在聊天里怎么显示，需要用 `project-composer-stability` 夹具先看一遍再定（尚未核实）。

### 3.5 失败与恢复

- **瞬时失败**（408 / 429 / 5xx / 超时 / overloaded）：LLM 层已按可重试处理（#345）。Project 层补一条：协调者回合以 `error` 结束时，宿主在退避后重新驱动一次，通知不丢。
- **仍失败**：阶段为「受阻」，行上一个「重试」按钮。不要求用户打字。
- **应用重启**：保留 4.2 的选择，重启后不自动恢复执行（安全切断），但每个需求行有「继续」，另有「全部继续」。重新开始的成员收到恢复说明：先检查目录和 git 状态，再重复任何对外动作。
- 失败的工具仍可用，用户可以直接在成员会话里接手。

### 3.6 面板：回答三个问题

打开面板依次回答：

1. **现在有什么要我做？**
2. **一切正常、在做对的事吗？**
3. **某一件事的来龙去脉是什么？**

据此：

- 顶部是**需要你**（等你回答 / 等你决定 / 受阻）；为空时不占位。
- 其下是**进行中**（有实时状态，见 #343），再下是**最近交付**。
- 计数 = 列表长度；一处一个概念（成员并入面板，见 #344；成果只在需求卡和成果历史里，项目资料对话框只留规则、笔记、偏好）。
- 行内直接给动作：回答、重试、继续、查看成果。
- 每个元素只回答上面某一个问题，否则删掉。

**与 #343 / #344 的关系：保留并合并。** 阶段条（安排 → 执行 → 汇总 → 交付）描述走到哪，§3.1 的标签描述在等谁，两者互补。若 §3.7 之后「汇总」不再是多数需求的必经步骤，阶段条相应改为三段。

### 3.7 上下文预算

- `project_read_store notes.md` 现在每次返回最近 10 条交付的完整正文（连同最多 20 条需求、20 条工作）。改为：交付默认每条一行（标题、结果、时间、摘要前 240 字符、附件数、遗留数），传 `requestId` 才返回该需求交付的完整正文；用户笔记超过 4,000 字符时只给前 4,000 字符，传 `fullNotes` 才给全文。界面读的交付列表不变。
- 协调者提示词从「每次恢复前都读」改为「需要时读」。
- 协调者提示词（约 15 KB，一整块）里属于机制的部分，移到工具描述和宿主校验中；提示词只保留角色和三段规则（§3.8）。

### 3.8 提示词整理（后期）

dsh-superagent 把团队可编辑的提示词分为三段：沟通、范围、交付，内置部分可覆盖，升级后默认变化时提示「默认内容已更新」并并排比较。Project 的 `charter.md`（用户规则，上限 16 KB）与它对应：把常用规则开关并入这三段，加「完整提示词」预览。只做整理，不增加新概念。

### 3.9 研究范围（待裁定）

现在没有任何能读网页的 Project 范围：`readonly` 禁用 shell，成员只有本地的读取与搜索。调研类需求（给一个链接，要求研究）做不了。

- **方案 A**：新增范围 `research` = `readonly` + 只读联网（取 URL、搜索），无 shell、无写入；记录取过哪些 URL。可选域名白名单。
- **方案 B**：不开联网，由 §3.3 保证不再空转：调研类请求明确说「做不了：没有联网」并停下，问你给材料。

## 4. 不做什么

- 不引入 Source / Eval / Policy，不让 Project 主动接活。
- 不引入 dsh-superagent 的代码。
- 不新增概念来承载业务需求；业务需求成为已有对象的属性或提示词。
- 不做任务表单、手动派单、成员管理 UI（沿用 4.2）。
- 不用更多的消息去解释噪音；噪音大就把提示词缩短、收紧。

## 6. 裁定（2026-11-03）

1. **范围**：只采用「注意力 / 阶段 / 提问 / 静默 / 恢复 / 面板」这一层，不采用 Source / Eval / Policy。
2. **研究范围**：方案 A，新增只读联网的 `research` 范围（§3.9）。
3. **分期**：六期全做，按 S1 → S6 的顺序，每期单独一个 PR、单独验收。S5 仍按 §5 的说明，在看到 S3 之后的数据后再确定具体做法。

## 7. 对 4.2 的修订

- 4.2 §1 规则 2：停下条件由两类增加为三类（§3.3）。
- 4.2 §1 规则 3 与 §3.2「人话状态」：替换为 §3.1 的阶段表（写明等谁）。
- 其余（单对话、需求流水线、项目记忆、原地写、撤销、生成式 UI 边界）保留。
