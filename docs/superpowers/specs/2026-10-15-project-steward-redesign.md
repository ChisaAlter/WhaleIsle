版本：4.2 · 2026-10-16。状态：**设计草案。** P1、P2 已在 `project-steward-p1` 分支实现（未提交）；客户端与服务端测试相对基线无新增失败。P3 及以后未实现。实现状态以 [功能资料](../../features/projects.md) 为准。

本文在 [3.2 产品重设计](2026-10-08-project-product-redesign.md)、[Team 架构](2026-10-08-project-team-architecture.md)、[提示词契约](2026-10-08-project-prompts.md) 的基础上重新定调：保留既有执行底座（协调者=Team Lead、worker=真实 teammate、原生 mailbox/settlement），把产品重心放到"**单对话 × 持续提需求 × 项目长期记忆**"的体验上。

术语：本文的"需求"等同既有文档的 Request/要求；"工作"等同 Workstream。

### 4.2 相对 4.1 的修订

| 项 | 4.1 | 4.2 | 原因 |

## 1. 唯一准绳：更好用

本设计不追求差异化，唯一目标是**日常用起来顺手**。一切取舍服从下面六条规矩。

1. **提需求零摩擦。** 用户照常说话。目标明确时 Lead 直接立卡并告诉用户一句"已记为需求：X"，卡片上可撤销；只有意图模糊（是在问还是要做？范围不清？）时才确认。提问、闲聊、追问结果留在对话里，不建卡。**绝不弹表单。**
2. **默认往前跑，只在真正的岔路口停。** 在一条需求的范围内，调查→开发→自测一路跑完不回头问；前一条做完，排队的下一条自动开始。只有两类情况停下找人：(a) 不可逆或对外的动作（由原生审批把关，如删除范围外文件、推送、全局安装），(b) 无法自行判定的真实抉择。其余只给一行"正在做 X"的回执。
3. **一眼看懂全局。** 看板只用人话状态；受阻必须写明原因与可行下一步。随时可以说"捋一下进度"，Lead 一段话汇总。
4. **系统记得项目，用户不用反复交代。** 项目规则写一次，之后每条需求自动遵守；决策自动留档。用户不需要维护记忆。
5. **看得懂它改了什么，能收回。** 每条需求交付时附带它改动的文件和 diff；不满意一句话"再改"，或"撤销"这条需求的改动（§5.3）。停止/失败状态写清楚，一条消息即可续。
6. **一个对话 + 一块看板。** 需求细节、diff、材料都在"点进去"后面；平时眼前只有对话与看板。

### 1.1 保留与放宽的约束

- **保留**（保护用户、让人敢信）：完成必须有真实证据（report + 原生结算 + 可见回复 + 持久化）；停止和冷启动不自动起模型；用户目录永不 reset/删除。
- **保留但改善体验**：同一目录同一时刻只有一条开发需求在写（避免互相破坏），但排队需求**自动接续**，用户无需再发消息；只读调查不受此限，可并行。
- **放宽**：取消"事事等用户消息"，范围内的后续阶段自动推进。

## 2. 概念模型

| 概念 | 产品含义 | 用户接触方式 |
| --- | --- | --- |
| Project | 绑定一个本地目录，拥有一条永久主对话、项目规则与资料 | 侧栏条目、主对话 |
| 主对话 / Lead | 项目的"家"，承接一切需求与提问 | 唯一主对话 |
| 项目规则 | 用户写的长期规则，`charter.md`，每轮自动注入 Lead 与 worker | "项目规则"页 |
| 偏好 | 既有 `preferences.md`，软性偏好 | 同一页面的第二栏 |
| 决策日志 | 每次交付和每次规则破例自动留档，`decisions.md` | 基本隐形，可查看 |
| 需求（Request） | 一个持续人类目标，带约束与完成条件，修订形成新版本 | 对话提出；看板上一张卡 |
| 需求改动 | 该需求从开始到交付在目录中产生的变更 | 卡片上的"N 个文件 · 查看 diff · 撤销" |
| Delivery（交付） | 对一个需求版本的结果 + 证据 + 未完成项 | 卡片结果页 / 主对话结论 |
| Worker | 后台成员，保留身份/cwd/历史 | 必要时查看过程 |

## 3. 需求流水线与看板

### 3.1 提需求

- Lead 区分三类输入：**提问/闲聊**（直接回答，不建卡）、**对已有需求的补充**（生成新版本）、**新目标**（直接立卡，模糊时确认）。
- 立卡后 Lead 用一句话告知，卡片提供"撤销"（等同取消，保留记录）。
- 一条消息可含多个目标；多条消息可共同补充一个目标。文件、转录、后台通知不能冒充用户消息。

### 3.2 需求状态机（人话）

```
讨论中 ──用户授权──▶ 排队中 ──宿主激活──▶ 进行中 ──完整交付──▶ 已交付 ──归档──▶ 已归档
   │                  │  ▲                 │  ▲                 │               │
   │                  │  └──移动顺序        │  └─原因解除/用户回复  │               └─恢复─▶ 已交付
   │                  │                    ├──▶ 受阻（原因 + 下一步）│
   │                  │                    └──▶ 部分交付（列出未满足条件，留在当前列表）
   │                  │                                            └─用户修订─▶ 排队中（新版本）
   └──────────────────┴── 任何未完成态 ──用户取消/撤销──▶ 已取消 ──重新加入──▶ 排队中
```

- 只读、文档类需求同样经"进行中→已交付"，交付内容是结论与文档，不要求代码 diff。
- 受阻原因结构化：等依赖 / 等目录空出 / 等容量 / 等用户回答 / 执行失败；每种都给一个下一步。
- 看板分组：当前（进行中、受阻、部分交付、排队中、讨论中）/ 已交付 / 已归档 / 已取消；当前组永远在最上，排队项显示"第 N 位"。

### 3.3 状态如何得出（不改存储结构）

人话状态是现有数据的**派生视图**，不新增持久化字段：

| 现有数据 | 人话状态 |
| --- | --- |
| `queue.state = discussing` | 讨论中 |
| `queue.state = queued` | 排队中（第 N 位） |
| `queue.state = active`，工作有 `blocked`/失败/等待原因 | 受阻 |
| `queue.state = active`，其他 | 进行中 |
| 当前版本有完整交付 | 已交付 |
| 当前版本仅有部分交付 | 部分交付 |
| `queue.state = cancelled` | 已取消 |
| `archivedAt` 存在 | 已归档 |

### 3.4 看板与"捋一下进度"

- 右侧 observer 的任务列表为常驻主界面；点卡片进入概览 / 工作 / 结果 / 活动。
- "捋一下进度"：Lead 已在每轮系统提示中获得队列摘要（`contextFor` → `projectFacts.queue`），并可按需读 store；回答用一段人话。

## 4. 项目长期记忆

### 4.1 层次与状态

| 层 | 维护者 | 存储 | 注入 | 状态 |
| --- | --- | --- | --- | --- |
| 项目规则 | 用户 | `charter.md`，上限 16KB | Lead 系统提示（每步）+ worker brief | **已实现（P1）** |
| 偏好 | 用户 | `preferences.md` | 同上 | 已有 |
| 队列/需求摘要 | 宿主生成 | catalog | Lead 系统提示（`contextFor`） | 已有 |
| 决策日志 | Lead 提供内容，宿主落盘 | `decisions.md`，append-only | 最近条目在预算内注入 Lead | P3 |
| 架构地图 | Lead，证据驱动 | 待定 | 待定 | 可选 P5 |

### 4.2 项目规则的语义

- 注入文案："Project rules (the user's standing rules for this Project)"。规则**高于模型自身默认与习惯**。
- 用户在当前对话中明确要求破例：Lead 确认一次，然后服从用户，并在回复中说明破例；P3 起破例写入决策日志。
- 超过 16KB：保存时拒绝并提示缩短，编辑器保留文本；若文件被外部改得超限，注入时按 UTF-8 边界截断并附提示，**不让 Lead 报错**。
- 旧项目首次读写时懒创建 `charter.md`；缺文件时注入为空。

### 4.3 项目规则页面

- 资料区页签依次为：成果 / 项目规则 / 偏好 / 笔记。「项目规则」对应 `charter.md`（必须遵守），「偏好」对应 `preferences.md`（尽量遵循，原名「项目要求」）。读写走现有 `store/read`、`store/write`。采用页签而非一页两栏，是为了直接复用现有编辑器的未保存提醒、保存与切换确认。
- 项目规则页包含：说明卡片、常用规则快捷开关（点击加入，再点移除）、用量条（超过 16KB 变红并禁止保存）。
- 未保存切换、保存失败保留草稿、超限提示，沿用 notes/preferences 的既有交互。

### 4.4 决策日志（P3）

- `project_deliver` 增加可选 `decision`（做了什么 / 为什么这样做）；宿主在交付成功落盘后追加到 `decisions.md`。
- 规则破例也追加一条（谁要求、破了哪条、原因）。
- 注入 Lead 的只是最近若干条，限 4KB；完整日志可通过 store 读取。

### 4.5 架构地图（可选 P5）

只有在决策日志证明"自维护记忆"确实提升体验之后才做。必须锚定 commit，并在相关文件变化后标记过期；过期内容不注入。

## 5. 执行模型

### 5.1 默认：原地写 + 同目录串行

- 开发需求在用户选定的目录中直接工作（与现状一致）。
- 同一规范目录（含父子目录、跨 Project）同一时刻只有一个写入者；只读工作不受限、可并行。
- 当前开发需求交付或取消后，队列自动激活下一条（现有 `queue.pump`），**无需用户再发消息**。

### 5.2 Momentum

- 在需求冻结的范围上限内，Lead/worker 自动推进 调查→开发→自测。
- 停下的条件见 §1 规矩 2；不可逆命令仍走原生单次审批。

### 5.3 需求改动与撤销（P3）

- 需求进入"进行中"时，宿主记录基线：Git 仓库记录 HEAD 与工作区快照；非 Git 目录用桌面端现有 `snapshot`。
- 交付时计算该需求的改动（基线 → 当前），卡片展示文件列表与 diff。若期间用户自己也改过目录，改动中会包含这些修改，需明确标注"可能含其他修改"。
- 撤销 = 对该需求的改动反向应用；有冲突时交给 Lead 处理并说明结果，绝不 reset 用户目录。
- 撤销本身被记录为一条事件，并写入决策日志。

### 5.4 可选并行（P4）

只有同时满足以下条件时，宿主才为开发需求自动开 Git worktree：

1. 目录是 Git 仓库；
2. 需求不依赖尚未交付需求的改动，且预计写入路径与当前写入者不重叠；
3. 环境可就绪：项目规则中声明了初始化命令（如 `pnpm install`），或依赖可共享。

合并：交付时由 Lead 把 worktree 分支合回原目录；冲突由 Lead 在 worktree 中解决并重新验证，解决不了则转"受阻"。顺序为**先合并、后记录交付**：合并失败不记录交付；合并成功但记录失败时，恢复流程检测到分支已合入，补记交付，不重跑工作。

## 6. 生成式 UI 的复用

复用既有 `html_render` 载体与 `visualReplyPage`、页面渲染器、附件权限、主题与 sandbox。**生成式页面是解释与呈现，不是完成证明。**

### 6.1 用在哪

- **交付结果页**：改了什么 / 验证了什么 / 前后对比 / 未完成项；复用 `delivery.pages`。
- **岔路口抉择**：方案 A/B 的取舍与影响面。
- **需求改动解释**：配合原生 diff，展示变更结构与影响范围。
- **进度概览（可选）**："捋一下进度"附一张快照。

### 6.2 边界

- 不新建渲染器；文件打开、执行记录仍是原生控件。
- 只关联交付回合真实发布的附件，不接受模型臆造的 attachmentId。
- 不为每条普通回复生成页面；只在流程/结构/对比确需可视化时生成。
- 遵守主题与无障碍，可折叠，不挤占对话和输入框。

## 7. 对 Agent Teams / Harness 的依赖

**P1–P3 无需修改 Team 源码。** 已核实：

- 系统提示每步重新渲染：`core/agent-loop` 的 `step()` 每步调用 `renderPrompt(assembly)`，有变化时通过 `systemPrompt.project` 提交更新。用户改规则后，Lead 下一步即可看到。
- 压缩保留系统头：`compaction-basic` 的压缩范围从第一个非系统节点开始，第 0 个节点的 `system/message` 不被压缩。注入内容不会因长对话丢失。
- Project 通过 `ctx.systemPrompt.section` 注入（`lead.js`：`project:scope` / `project:charter` / `project:preferences`），worker 通过 brief 注入。

**P4 可能需要**：显式的 Lead 可调度状态，用于替换 `queue.js` 中依据事件快照推断 Lead 忙闲的逻辑。在 P4 之前保持现状，不单独改动。

## 8. 保留的正确性

- **report ≠ 完成**：任务完成需当前 report 与匹配的原生结算一致（沿用 `teamAdmission` 的 `task:complete`）。
- **需求不可变 + 版本化**：委派引用确切版本。
- **停止 / 冷启动不自动起模型**：只有新的用户消息能续。
- **用户目录安全**：不 reset、不 stash、不删除；撤销只反向应用该需求自己的改动。

## 11. 验收场景（可执行）

每条均需在真实桌面应用中观察，并核对 Session/catalog 记录。

1. **建项目**：选择目录 → 无模型运行、无新分支；打开 Lead 主对话。
2. **连续提需求**：一分钟内发 3 个开发目标，第 2 个依赖第 1 个 → 看板显示 1 进行中、2 和 3 排队（第 1、2 位）；第 1 条交付后，第 2 条在无用户消息的情况下自动开始。
3. **闲聊不建卡**：连续问 5 个问题 → 看板无新卡。
4. **规则生效**：在规则页写"新增函数必须有测试" → 下一条开发需求的 worker brief 含该规则，交付证据中包含测试结果。
5. **规则破例**：用户说"这次不用写测试" → Lead 确认一次后执行，回复中说明破例；P3 起决策日志有记录。
6. **规则超限**：保存 20KB 规则 → 被拒并提示，编辑器保留文本。
7. **长对话**：手动触发压缩后，问"项目规则有哪些"与"现在进度如何" → 答案与规则页、看板一致。
8. **停止与恢复**：进行中时停止 → 卡片显示已停止；重启应用 → 无模型运行；发"继续" → 恢复。
9. **撤销（P3）**：撤销一条已交付需求 → 其改动的文件恢复；有冲突时 Lead 给出说明；用户目录其他内容不变。

## 12. 不做什么

- 不追求与 Cursor / Claude Code 的差异化卖点。
