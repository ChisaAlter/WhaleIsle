# Project 简化设计：普通对话，Super Agent 协作

日期：2026-11-13 · 状态：独立工作分支开发中 · 跟踪：[Issue #388](https://github.com/ChisaAlter/WhaleIsle/issues/388)

**Project 的主页面就是完整的普通对话页，右侧只有一个可折叠的悬浮任务栏。主 Agent 负责理解、调度、协调、验收和交付，实际工作由原生 Team / Subagent 执行。**

本文记录用户本轮确定的方向，并给出可直接用于开发的具体方案。用户已授权实施；[实施计划](../plans/2026-11-13-project-superagent-redesign-plan.md)说明开发顺序与完成标准，[源码研究](../../research/2026-11-13-project-superagent-source-notes.md)区分官方原型的实际实现和本项目需要补的能力。

## 1. 本轮确定什么，暂时不做什么

### 1.1 用户已确定的产品方向

1. 简化当前 Project，不再让用户理解多层要求、成员、阶段、材料与验收页面才能使用。
2. 聊天区具备普通对话应有的功能，不建设一个能力较少的专用聊天页。
3. 右侧提供可折叠的悬浮栏，呈现类似参考图的任务卡片。
4. Project 默认启用 **rc.2 原生 Team 和原生 Subagent**。修改 Project 适配原生能力，不以关闭原生能力来迁就旧 Project。
5. 主 Agent 不承担实际开发；它负责分发、排期、协调、验收与对话。
6. 工作执行期间，用户仍可聊天并连续提出多个任务；主 Agent 判断哪些并行、哪些排队。
7. 参考 DeepSeek 公开的 `dsh-superagent-prototype`，研究实际执行机制，而非只复制一段人格提示词。
8. GitHub 仓库接入、项目知识图谱、项目可视化属于后续路线图，现在不实施。

### 1.2 本文选定的落地方式

- 普通 Agent 与 Super Agent 首先是**职责、工具权限、执行和任务生命周期的区别**，不要求固定使用两个不同模型。
- 多个已授权要求可以同时有工作执行；调度单位是具体工作，不是把整项要求永久锁成一个串行槽。
- 主 Agent 可以读取现有成果、相关文件和差异以判断是否满足要求，但不承担仓库调查、写文件、运行命令或实际测试等执行工作。
- 复用原生运行、成员、消息与结算身份；Project 只补充用户目标、调度约束、验收和卡片视图。
- 任务栏是唯一默认进度入口。详细记录、旧资料、成员会话仍可按需访问，不在首页并列摆放。

这些是本设计的推荐默认值，不代表当前应用已经具备这些行为。

### 1.3 与旧设计的取舍

本设计替代旧 Project 设计中以下目标：

- “一个 Project 同时只有一个活跃要求，写入必须等整项要求交付后才轮到下一项”。
- “Project 的协作必须由旧实验 Team 独占，原生 Subagent / Team 入口应被拦截”。
- 以要求卡内多页签、四阶段轨道、独立成员页和材料页作为默认阅读路径。

保留旧设计中有效的约定：真实目录绑定、持续主对话、用户要求来源、成员身份与历史、原生审批、成果依据、停止与排空、重启不擅自恢复工作。旧文档和历史验证保留为旧版本记录，不能据此约束新方案继续串行或禁用原生能力。

## 2. 用户怎么使用

### 2.1 一段典型流程

用户打开 Project，在普通输入框中说：“修复登录错误，另外检查文档里有没有过时说明。”

主 Agent 把它组织成两件可追踪的工作：登录修复、文档检查。若检查不依赖修复且没有写冲突，可以立即并行；若接下来要更新依赖同一接口的说明，该部分等待修复结论。主 Agent 简短说明已安排的真实动作，然后结束当前回合，不在前台等待所有成员。

用户接着问“登录为什么可能失败？”或追加“先保证兼容旧账号”。主 Agent 继续响应，把有效补充交给对应工作，不要求用户另开对话，也不把新消息全部塞进开发任务的尾部。

成员完成后，主 Agent 检查成果与证据。不满足要求则退回原工作继续；满足要求则在主对话交付。任务卡保留结果、文件和验证入口。

### 2.2 普通对话与 Project 的区别

| 项目 | 普通对话 | Project |
| --- | --- | --- |
| 对话与输入体验 | 现有普通对话 | 同一套对话和输入组件 |
| 主要执行者 | 当前 Agent 按普通策略执行 | 主 Agent 协调，工作 Agent 执行 |
| Team / Subagent | 按普通设置和用户选择 | 默认可用，按任务选用 |
| 多件工作 | 普通会话语义 | 有持续任务、依赖、排期、验收和成果关联 |
| 任务执行期间聊天 | 原有行为 | 后台工作不占用主 Agent 的整段执行期 |
| 进度 | 原有工具/任务展示 | 另有可折叠任务栏，聚合真实工作状态 |

“默认启用”不等于每句话必须派人、每项任务必须创建团队或固定多名成员。已知事实和已有结果可直接回答；一名成员能够完成的工作不拆成固定流水线。

## 3. 页面结构与交互

### 3.1 复用普通聊天，不创建第二套聊天产品

保留消息流、流式输出、模型选择、权限与审批、附件、图片、工具详情、文件预览、复制/导出、搜索、草稿及原有导航能力。实现时逐项核对当前普通对话入口，不能只复制消息外观。

模型选择改变主 Agent 的后续模型；已运行成员不被静默切换。新成员采用创建时有效的模型/预设规则，并在执行详情中可查。Project 协调者角色不能通过模型选择变成开发者。

编辑重发和分支操作保留既有消息历史。重发不能无条件重复已接纳的任务；从主会话分叉的普通对话不自动取得原 Project 的调度权。Project 的主会话、目录和运行身份仍有明确归属。

### 3.2 右侧可折叠悬浮任务栏

```text
现有导航       普通对话区                         浮动任务栏
               用户要求、解释、关键结果          任务进度       [收起]
               ……                               需要处理
                                                [具体问题与回答入口]
                                                进行中 / 等待
                                                [修复登录 · 执行中]
                                                [更新文档 · 等待接口结果]
               原有输入框与控制                  最近完成
                                                [检查配置 · 查看结果]
```

- 展开时是一列卡片，不再默认呈现成员管理、要求版本、阶段轨道等结构。
- 首次进入默认收起成右侧的紧凑入口；用户展开后记住该 Project 的展开状态、滚动位置和阅读对象。
- 收起时显示真实的活动数和需要处理的提示，不重复显示整个阶段面板。状态未知显示连接/读取异常，不伪装成零任务。
- 无任务时不创建示例卡或欢迎任务；展开后只显示简短空态，用户仍从普通输入框提出要求。
- 新消息和任务状态变化不自动展开、不抢焦点、不把用户正在看的卡片移走。
- 宽窗口在聊天正文之外安排悬浮栏，不能遮住输入框、标题栏和文件操作。空间不足时使用覆盖式抽屉，不把聊天内容挤成不可读窄列。
- 已有文件/浏览器右栏继续工作。任务栏不覆盖文件编辑器的关键区域；同侧空间不足时切换查看表面，并保留各自状态与文件草稿。
- 面板有自己的有界滚动区。关闭只关闭视图，不取消任务；切换 Project 不能混入上一项目的卡片。

参考图用于卡片的信息关系：标题、状态、简短原因、结果和必要操作。不要照搬其重复警告、大面积状态染色、无意义分类或顶部多入口。视觉沿用鲸屿设计语言、主题 token 和共享原语，不另造一套皮肤。

### 3.3 一张卡片说明一件有意义的工作

默认首层只有：

1. 以目标/成果命名的标题，例如“修复旧账号登录”，而不是 Session ID 或“development worker”。
2. 当前状态；排队、受阻或失败时附一条具体原因。
3. 与该状态匹配的动作：查看执行、查看结果、停止、取消排队或回答问题。

展开详情后再显示主 Agent 的安排、执行成员、依赖工作、报告、验证、文件、实际目录、运行记录和历史。内部 ID 不进入默认卡面。一个目标可以有多个执行阶段，但不能为每次模型回合、工具调用或重试都新增一张顶层卡。

需要处理的事项在前；活动工作其次；最近完成最后。历史按需分页。用户阅读期间保持卡片身份和位置，完成状态原位更新；重新进入列表时再应用分组顺序。

### 3.4 操作范围必须明确

- 普通输入框的停止按钮停止主 Agent 当前回合，维持普通对话语义；不默默取消所有后台工作。
- 单项卡片提供“停止这项工作”或“取消排队”。
- 面板更多菜单提供明确的“停止全部项目工作”；涉及活动工作时使用既有确认机制。
- 归档 Project 仍停止其拥有的工作并等待排空，保留历史与文件。恢复归档不自动执行旧任务。
- 问题在主对话提出；卡片的回答入口复用普通消息链路，保留当前草稿，不能绕过权限通过隐藏 RPC 直接开工。

以上停止入口是本次简化后的目标，实施时需要同步旧快捷键、标题栏、输入框与后台活动提示，避免旧版“主对话停止等于全停”的行为残留。

## 4. Super Agent 的职责与执行约束

### 4.1 主 Agent 做什么

- 理解完整要求和仍有效的约束，区分讨论、已授权执行和已有工作的补充。
- 按成果拆分必要任务，选择 Team 协作或独立 Subagent，指定依赖、执行范围和验收条件。
- 依据真实执行状态安排并行、排队与优先级；在原授权内推进必要的后续阶段。
- 回答用户，协调接口与资源冲突，把补充送给正确的成员。
- 阅读报告、相关成果与证据，判断是否达标；安排必要的验证，退回修改或接受成果。
- 向用户交付结果、位置、重要验证和仍缺少的条件。

主 Agent 不编辑项目文件、不运行 shell/构建/测试、不调用会修改外部状态的执行工具。仓库系统性调查、网页研究、代码、文档、测试和整合作业都由工作 Agent 承担。为验收而读取具体成果与差异允许使用受控只读能力；不能用命令工具的“只读参数”变相获取执行权。

权限在 Host 的真实执行边界生效，而非只靠提示词。检查覆盖原生工具、插件工具和间接调用；普通会话不继承该角色限制。主 Agent 管理任务和写入 Project 自身的调度/验收记录不等于获得仓库写权限。

### 4.2 原生 Team 与 Subagent 各司其职

- **Team** 用于需要成员协作、共享任务上下文或相互交接的工作。
- **Subagent** 用于边界清楚的调查、执行或验证；简单任务不必先搭建团队管理结构。
- rc.2 原生 Team 的成员就是 Subagent 树中的成员，Team 提供共享任务板，不另建成员运行时。Project 不把二者当成必须互斥的模式，也不为一次执行创建两份独立任务事实。
- 不全局禁用 `subagent`、`subagent_fork`、原生 Team 工具或 UI 来维持旧 Project。针对 Project 的角色、工作归属和权限约束应用在实际执行上；不符合约束的具体操作给出原因。
- 后代 Agent 仍须具有可追踪的任务归属、有效授权与资源范围。成员确有必要再委派时，仍使用原生机制，并保持祖先任务的停止与结果关联；不得借嵌套委派脱离约束。
- 普通 Team/Subagent 的入口、配置、会话和权限行为保持不变。

默认启用能力与授予执行权限是两回事：只读要求依然不能写文件；单次审批不能被缓存为未来所有命令的许可。工具来自插件、MCP 或网页内容，不因此获得用户授权。

### 4.3 持续聊天与后台执行

主 Agent 接纳并派发工作后及时结束当前安排回合，让用户继续交流。不能长时间调用阻塞等待工具占住主对话。

同一主 Agent 不同时运行两个写同一会话状态的回合。用户在其输出期间发送的消息沿原生输入接纳/转向机制处理；这种短暂的模型回合串行不能变成“后台任务完成前一律不接新要求”。

成员结果在主 Agent 忙碌时仍持久记录，按原生接纳机制交给当前或后续协调回合。通知只提供已有工作的结果，不创建新的用户授权；一次结果不能重复触发两个验收或重复交付。无需用户处理的日常状态留在卡片，重要成果、阻碍和决策才回到主对话。

## 5. 调度：由主 Agent 决策，Host 保证执行事实

主 Agent 决定工作拆分、依赖和优先级；Host 核对有效授权、依赖、当前资源占用和原生容量后接纳。不能只说“并行执行”，底层仍把所有要求串成一个全局队列。

### 5.1 按工作调度，不按整个要求一刀切

同一要求可以有多个工作；不同要求也可以同时推进。讨论中的想法没有执行权。用户明确要求“先 A 后 B”时保留顺序；没有该约束时由主 Agent 根据收益和冲突安排，不反复把排期问题交还给用户。

| 情况 | 默认安排 | 卡片应说明 |
| --- | --- | --- |
| 两项独立只读调查 | 有容量就并行 | 各自实际运行状态 |
| 独立目录且没有共享生成物/服务冲突的写入 | 范围明确后可并行 | 各自执行目标 |
| 同一目录内不同、可核实且受约束的写入范围 | 明确所有权，核对共享依赖后可并行 | 必要时展开资源安排 |
| 同文件、重叠范围、共享锁文件或不能隔离的全仓命令 | 排队或先调整拆分 | 等待哪项工作释放什么资源 |
| B 必须使用 A 的接口或成果 | B 的相关工作等待 A 的有效结果 | 等待哪份结果 |
| 已有用户认可的独立 worktree 安排 | 可在独立目录并行，整合另行安排 | 尚未整合不能显示交付已落入主目录 |
| 权限、凭据或容量不足 | 只阻塞受影响工作 | 具体缺项与可用处理入口 |

不把“模型承诺不改某文件”当成已经实现的写入隔离；任意 shell、构建和代码生成还可能修改共享目录或占端口。若实际工具无法保证细粒度范围，该项按较大的真实资源范围安排，通常是串行。不能为追求并行偷偷初始化 Git、创建分支/worktree，或覆盖用户未提交内容。

### 5.2 何时推进等待工作

- 等待项持久保存，带具体原因，不只有一个含糊的“排队中”。
- 资源释放、依赖结果可用、容量恢复或用户有效回答后重新评估受影响项，不靠无限轮询模型。
- 成员空闲、口头说完成或退出都不是业务验收通过；实际后台 Job 未结束时不能释放其写入占用。
- 依赖引用具体成果/修订。后续修改使依据过期时，只把受影响工作标为需复核，不抹掉历史结果，也不把所有任务全部重跑。
- 一项失败、被取消或等待审批，不自动冻结其他独立工作。依赖它的后续工作保持可见，并由主 Agent 调整或向用户说明。

## 6. 任务事实、验收与交付

### 6.1 只保留必要的业务对象

| 对象 | 保存什么 | 不负责什么 |
| --- | --- | --- |
| Project | 真实目录、主会话、长期约定、生命周期 | 不复制普通聊天消息 |
| 要求 Request | 用户目标、有效约束、来源消息、修订、完成条件 | 不作为全项目唯一执行锁 |
| 工作 Workstream | 可交付任务、归属要求、依赖与原生执行引用 | 不另外实现一套成员/mailbox |
| 成员报告 | 本次工作成果、验证、剩余事项与精确运行引用 | 不直接等同验收通过 |
| 验收与交付 Delivery | 对哪版要求、哪些成果作了何种判断，交给用户什么 | 不用一个“已完成”覆盖失败或部分结果 |

原生 Session、activation/run、成员、消息投递和结算继续由原生模块负责。Project 任务状态是这些事实加业务验收的视图；不要把进度组件本地状态反向当作运行权威。

原生任务的执行完成状态与 Project 的业务验收是不同事实，不能为了显示“待验收”篡改原生运行结果。Project 保存接受/退回及成果修订的关联；依赖某份已验收成果的工作，除原生依赖就绪外，还要在派发时核对这份验收。退回修改沿用原生任务更新/续接契约，不伪造一次新的完成事件。

### 6.2 用户看到的状态

```text
已接纳 → 排队/等待依赖 → 执行中 → 待验收 → 已完成
                           ↑          │
                           └─ 退回修改 ┘
```

需要输入、受阻、失败、停止中、已停止和已取消是明确分支，不得挤成同一个“等待”。执行结束后仍需验收的工作显示“待验收”，不能提前转入已完成列表。

停止和取消的对象也不同：取消尚未启动的工作不伪造执行失败；停止正在运行的工作先显示停止中，实际排空后再显示已停止。继续必须来自明确用户要求或仍有效授权内的正常阶段推进，停止/取消后旧消息不能自行重启。

### 6.3 验收需要什么

工作交给成员时应包含目标、范围、依赖和完成条件。成员报告给出实际改动/结论、成果位置、实际检查、未满足事项。Host 用原生执行身份关联报告，不能接受其他任务的一份旧报告来完成当前任务。

主 Agent 将证据与要求对照：

- 足够：接受成果，在主对话完成相应交付。
- 明确不满足：将具体缺口退回原工作，保留已有正确成果与历史。
- 证据不足：安排有针对性的验证工作，不自己运行测试，也不机械再造一条完整审查链。
- 部分满足：交付部分结果并说明剩余条件，相关卡片保持未完成状态。

代码测试通过不证明界面好用；可见界面仍需要实际渲染和交互证据。开发者自报测试结果可以是证据，但不是自动验收结论。主 Agent 的接受是代理内部验收，不能伪装成人类签署或用户已同意合并/发布。

## 7. 数据、权限与恢复

- 保留既有 Project、要求、主/成员会话、报告、笔记、长期约定、附件、工作目录和用户草稿。简化默认界面，不删除旧数据。
- 新卡片复用稳定身份映射。历史旧实验 Team 数据可以只读解释，不需要把它继续装配成新执行后端才能查看。
- 升级先关闭旧执行接纳，再核对正在运行的工作；不能让新旧两套控制器同时给同一任务派发。
- 迁移不自动重放历史消息或把“曾经排队”视为升级后的新授权。无法确认的运行显示需恢复/核对，不显示成功。
- 应用重启和 Project 恢复首先恢复可读事实，不自动启动旧开发任务。用户明确继续后再核对当前目录、权限、依赖与运行归属。
- 文件预览、编辑、命令、网络和外部服务继续走现有授权。取消审批、停止或归档后迟到的允许回执不能启动任务。
- 只停止和清理该项目拥有的原生运行及其 Job，不按进程名杀其他程序，不 reset/stash/删除用户目录。

- `domain.js`、`requirements.js`、`approvals.js`、目录桥和原生 continuation 对接中已有可复用的历史、权限、来源与停止能力；迁移逐项保留，不重新发明通用运行平台。

[PR #387](https://github.com/ChisaAlter/WhaleIsle/pull/387) 的既有 CI 证明旧候选的上游整合结果，不证明本文的新 Project 行为。新方案涉及的产品路径必须在后续实现候选重新验证。

### 8.1 官方原型能参考到哪一步

源码研究固定在 Super-agent 提交 `8c32a9dc5d72c033816c6a8110b37f40cf94fba4`，具体来源见[研究说明](../../research/2026-11-13-project-superagent-source-notes.md)：

- 原型主 Session 是 router，通过自有派工机制启动 worker；router 没有原生 Subagent 工具，却保留 shell。它的角色配置不能直接当成本文的协调者预设。
- 原型把技术实现与验证交给 worker，带 PR 的 ready 结果等待人审；本文要求的主 Agent 技术验收和退回闭环需要另行实现。
- 原型的 WorkerSlots 提供容量队列及人的追问优先，不判断文件、服务等资源冲突。
- rc.2 原生 Team 与 Subagent 已共用 Agent 树；Team 的 `writeScopes` 只产生冲突警告，不强制隔离。原生 Subagent 容量满会拒绝，不替 Project 保存业务等待项。

因此采用原型的异步分工、持续任务和结果回收思路，沿用 Harness 原生执行能力；Project 自己承担业务接纳、资源排期、验收和简化界面的适配。原型的外部事件入口、无人值守权限和自动恢复策略不随之引入。
