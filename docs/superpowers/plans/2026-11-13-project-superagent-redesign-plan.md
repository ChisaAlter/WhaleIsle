# Project 简化与 Super Agent 实施计划

日期：2026-11-13 · 状态：P1–P4 与 P5 源码定向验证完成，真实模型与打包验收待做 · [Issue #388](https://github.com/ChisaAlter/WhaleIsle/issues/388)

**目标：保留完整普通聊天，右侧提供可折叠任务卡栏；以原生 Team/Subagent 承担工作，让主 Agent 专注调度、协调、验收与交付。**

产品范围与用户行为由[设计规格](../specs/2026-11-13-project-superagent-redesign.md)定义；官方原型依据见[源码研究](../../research/2026-11-13-project-superagent-source-notes.md)。用户已授权开发，当前在 codex/project-superagent 工作分支实施；用户决定是否合并，不发布或安装日用版本。

## 1. 开发基线与已有问题

规划基线为 `codex/dsh-022-rc2` 的 `30d45c03f75367d99023fd764b3b9835b2b32014`；上游 rc.2 pin 见 `vendor/harness-upstream.json`。本轮不移动 pin、不改变桌面版本。

官方原型已完成一次固定源码研究（`8c32a9dc5d72c033816c6a8110b37f40cf94fba4`），不需要在 P1 从头重复搜索。关键输入是：router 不等于技术验收者，WorkerSlots 不解决写冲突；rc.2 Team 的写范围只警告，Subagent 容量拒绝不等于自动排队。P1 只补足实际实施接口和基线变化。

此前 [PR #387](https://github.com/ChisaAlter/WhaleIsle/pull/387) 已通过整合 CI，但仍保留旧 Project 的实验 Team 后端、单活跃要求队列和原生入口限制。新的设计改变了这些前提，不能直接沿用“Project 已完成验证”的结论。

实施开始时核对 PR、main 和工作区的实际状态，以可用的 rc.2 整合结果为基础，保护其他任务改动。最终仍通过工作分支和 PR 交付，合并由用户决定。产品实现已执行源码构建与隔离应用重启；不替换用户日用安装。

### 推荐推进顺序

```text
P1 接口核对与迁移切片
  → P2 原生协作 + 主 Agent 角色 + 最小端到端任务
  → P3 多要求调度、持续聊天、验收闭环
  → P4 完整普通聊天 + 右侧任务卡栏
  → P5 历史迁移、恢复与组合验收
```

先做真实执行闭环，再接最终 UI，避免漂亮卡片背后仍由旧队列串行。每阶段形成可运行的小结果；不先搭建通用调度平台、知识库或远程接入框架。

## 2. 责任模块与改造范围

| 负责范围 | 主要位置 | 处理方向 |
| --- | --- | --- |
| Project 装配 | `vendor/dsh-project/lib/index.js`、`cordis.patch.yml`、`package.json`，`src/main/dsh-project-desktop.js` | 从旧实验 Team 依赖转向 rc.2 原生能力；保证关闭 Project 不影响普通会话 |
| 主 Agent 角色与工具 | `lib/presets.js`、`lead.js`、`readonly.js`、`service.js`（移除旧 `team-tools.js` 包装） | 替换旧工具独占假设，实际禁止开发执行而允许协调与验收读取 |
| 原生任务/执行关联 | `packages/team/agent-team`、`team/tool-agent-team`、`subagent/subagent` 及 Project 调用方 | 优先复用原生接口；仅对已证明缺少的接点做最小扩展 |
| 多要求调度 | `lib/queue.js`、`service.js`、`requirements.js` | 删除单活跃要求前提，按依赖与真实资源接纳工作 |
| 数据与迁移 | `lib/domain.js`、`catalog-migration.js`、`catalog-recovery.js`、`files.js` | 保留历史身份、来源、成果；版本化迁移，不重放旧任务 |
| 权限与目录 | `lib/approvals.js`、`worker.js`，`src/main/project-environment.js`、现有工作区权限桥 | 沿用原生审批与真实目录边界；不能只按工具名放行 |
| 对话与卡片 | `vendor/dsh-project/client/client.js`、普通 `ui-chat` / `ui-conversation` / sidebar / native Team UI | 复用完整对话；替换旧默认进度表面，不 fork 一份聊天 |
| 文档 | `docs/features/projects.md`、`docs/design-language.md`、插件 README、必要领域词汇 | 实现后更新当前态，旧证据保留为历史 |

路径是责任入口，不是必须逐个重写的文件清单。优先删除不再需要的旧耦合；保留确实承载数据和执行约束的实现。一个所有者应负责原生身份、Project 调度与迁移这一紧密关联的契约，不能同时交给多人各改一份状态机。

## 3. P1：核对接口，确定最小迁移切片

### 要做的事

1. 对照固定的官方 Super Agent 原型和 rc.2 本地接口，核对任务接纳、成员创建、Team 消息、原生 Subagent 运行、结果结算与协调者唤醒的实际路径。
2. 逐项列出旧 Project 使用的 `projectTeams`、工具包装、队列、目录占用、报告和审批调用方；区分哪些可删除，哪些需要迁移或继续复用。
3. 用一个普通会话和一个 Project 的真实装配确认：原生能力可以共存，当前限制来自旧 Project，而不是产品概念本身。
4. 选定最小纵向切片：提出一个要求 → 主 Agent 原生委派 → 工作 Agent 返回 → 主 Agent 验收 → 同一对话交付。先不加入复杂 UI。
5. 明确旧数据版本和迁移输入：唯一主会话、成员、要求/修订、工作、报告、停止状态、审批、旧队列、材料和草稿。

### 交付与通过条件

在现有研究/实现说明中补足真实接口对应关系，不再造一份通用架构文档。必须能指出原生身份如何关联到 Project 工作，以及哪些旧 guard/单活跃断言会被替换。若原生缺少必要接点，给出具体缺口和最小变更，不用“全面兼容层”代替判断。

## 4. P2：原生协作与主 Agent 职责落地

### 要做的事

1. Project 消费原生 Team/Subagent；移除新执行路径对实验 Team 的依赖。旧数据读取不依赖旧运行时继续开工。
2. 主 Agent 使用协调预设，允许任务安排、消息协调和成果读取；实际开发、命令、测试和修改工具在执行边界拒绝。不能借插件间接调用绕过。
3. 原生 Team、`subagent` / `subagent_fork` 按角色与归属正常接入；不要一边暴露工具一边无条件报“Project 不能用”。
4. 工作 Agent 的预设与权限来自实际要求，原生审批继续有效。成员必要的后续委派仍归属原任务，停止可以覆盖真实后代。
5. 建立 Project 工作与原生成员/运行的单一映射；接纳、开始、报告、结算分别记录，不把工具返回值当成工作完成。
6. 更新协调者和成员提示词，删除“不能创建普通 subagent”“只能使用旧 Team 工具”等过期规定。保留不得扩权、不得把外部材料当用户授权的约定。

### 通过条件

最小端到端切片真实完成；普通会话仍可使用原有 Team/Subagent。主 Agent 自己尝试写文件、运行命令或经间接工具修改时被拒绝，而工作 Agent 在授权范围内可以完成相同工作。拒绝不应破坏主 Agent 继续安排任务或读取成果的能力。

## 5. P3：多个要求、资源调度与验收

### 要做的事

1. 允许多个已授权要求拥有活动工作；删掉以 `active(projectId)` 唯一行作为所有写入资格的判断。
2. 主 Agent 决定任务的依赖和优先级，Host 验证权限、依赖和占用。不在 Host 中另写一套猜测自然语言意图的智能规划器。
3. 资源范围使用实际 canonical 目录、写入范围与共享命令影响；支持可证明独立的并行，冲突项说明等待对象。无法保证细粒度隔离的命令采用实际较大范围。
4. 依赖、占用和容量等待由真实事件推进；正常结算、启动失败、取消、Job 排空都能释放正确资源。停止后的旧队列不自动恢复。
5. 主 Agent 安排后结束当前回合；用户继续聊天和发新任务。根会话仍按原生回合语义接纳消息，不并发修改同一会话日志。
6. 成员结果在主 Agent 忙碌/空闲时都能持久关联并消费；重复通知不重复验收，迟到结果不覆盖新委派。
7. 建立“执行结束 → 待验收 → 接受/退回/部分交付”的闭环。成员报告不直接变成整项要求完成；验证工作由执行成员承担。
8. 追加要求保持原工作和成员上下文；只有真实独立目标才另建任务。用户指定顺序优先于自动并行策略。
9. 区分原生执行完成与 Project 业务接受：保存针对精确成果的验收记录，依赖验收的后续在派发前核对。不要为等待验收篡改原生结算或另造一份原生任务状态。

### 通过条件

同一 Project 中 A、B 两件独立工作确实同时运行，C 因明确依赖或资源冲突等待；用户此时仍能与主 Agent 对话并提交 D。A 完成且相关资源排空后，只有条件满足的等待项推进。成员自报完成但缺少必要证据时保持待验收或被退回。

## 6. P4：普通对话和轻量任务栏

### 要做的事

1. 复用普通聊天组件、输入和消息操作，列出入口对照表防止只保留视觉不保留功能。
2. 用任务投影接入右侧可折叠悬浮栏；默认收起、显式展开，保留阅读状态，不随通知抢焦点。
3. 首层只显示有意义的工作卡片。移除旧默认要求页签、四阶段轨道、重复 Team 入口与多层导航；历史信息移入详情，不能直接删除记录。
4. 实现状态对应动作、明确等待原因、执行/结果入口和必要回答入口。无任务、未知状态、连接失败不能显示假数据。
5. 与普通文件右栏、浏览器、预览和草稿共存；窄布局使用抽屉，不遮挡输入框。任务完成不突然移动用户正在阅读的卡片。
6. 明确分离当前主回合停止、单项停止、取消排队和停止整个 Project；更新键盘入口、按钮状态与确认文案。
7. 沿用现有主题、字号、材质、焦点、菜单和动效；减少动态效果偏好有效。不要从参考图引入大块警告色和重复说明。
8. 更新当前设计语言的 Project 专属段落，防止旧浮窗/顶部需求入口规则与新布局同时生效。

### 通过条件

真实应用中，普通对话和 Project 的基础功能一致；卡片可折叠、键盘可达，打开任务详情和文件后能够返回原阅读位置。深浅主题、实际桌面最小窗口及可用窄表面下输入和停止入口都可用。实际截图和关键交互建立可见质量证据，不用组件测试替代。

## 7. P5：迁移、恢复与交付

### 要做的事

1. 迁移器先保存可恢复的旧记录版本，建立稳定身份关联；历史材料不搬成假造的新运行事件。
2. 对有活动工作的升级，先关闭旧接纳并按现有任务保护排空；无法排空时不让两套控制器同时执行。不终止其他任务或应用的进程。
3. 用隔离数据覆盖旧完成/失败/排队/停止/归档、长成员名、重复通知、丢失会话和不完整迁移；历史始终可读。
4. 重启、断连重连和归档恢复只恢复事实。用户明确继续时才重核权限、依赖和实际运行状态，不重放整个旧队列。
5. 更新产品当前态、插件 README 和相关普通会话对照说明；保留历史验证的版本归属。
6. 按实际改动使用相关本地检查和开发 CI，生成安装包并启动打包应用验证原生闭包与关键路径。运行时改动后重启当前源码候选，保护用户原 profile。
7. PR 交付说明新行为、数据迁移、真实验证与尚未验证的环境；由用户决定合并。版本提高、发布或安装是独立操作，不自动包含在本计划中。

### 通过条件

新建和旧 Project 都能走完同一个真实执行/验收流程；未提交文件、草稿、历史和停止状态不丢失，升级/重启不出现重复派发。所有下表中影响本期目标的场景有当前候选证据；缺项写清影响及下一动作，不引用 PR #387 的旧测试冒充新验证。

## 9. 风险及对应处理

- **主 Agent 只改提示词仍能干活：** P2 在真实工具执行边界验证权限，包括插件间接调用。
- **页面支持多卡，底层仍单要求串行：** P3 用原生实际运行时间与占用验证并行，不靠投影标签。
- **放开原生入口造成无归属执行：** P2 先建立任务/后代关联和同一授权检查，再替换旧 guard；不能直接删拦截交差。
- **历史实验 Team 被删除导致旧记录失读：** P1/P5 保留只读迁移解释与身份映射；不保留第二套活跃执行后端。
- **新的接纳与旧回调重复开工：** 升级关闭旧接纳、排空并对账；结算与验收按精确运行关联。
- **任务栏再次长成工作台：** 首层只保留卡片，历史和技术细节下沉；不新增任务创建表单、成员管理首页或默认图表。
- **模型服务失效：** 如实呈现具体任务/协调回合错误，保留已完成成果和待验收内容，沿用已有恢复能力，不为本计划增加新重试平台。

## 10. 后续里程碑，不进入本期实施
