## User behavior

Projects have their own category and creation entry below ordinary workspaces in the existing sidebar. Selecting a Project opens its unique continuing Lead conversation bound to the authoritative local directory. Creation performs no model run, delegation, Git initialization or branch creation. Non-Git directories are supported. The ordinary conversation controls select the model and permissions; Project has no separate model setup or workbench. The conversation header distinguishes the real directory action from the Project overview action.

A Project-owned Lead is not projected into an ordinary Workspace directory or duplicated as an ordinary conversation. Registered directories retain their ordinary membership and actions. Project entries use their own rename, archive and restore actions while retaining the original Lead identity and execution cwd.

Project rename and archive shortcuts use the same Project actions as the row context menu, including active-work confirmation. They cannot rename or archive only the underlying Session. The main conversation remains unique: ordinary Session fork shortcuts and reply-branch controls are unavailable, and the Host rejects direct fork requests before creating a child.

Describe work in the main conversation. The Lead delegates to actual native Team members and tasks. Workers retain their original Session, preset, fixed cwd and owned worktree through explicit continuations. Within the active requirement, read-only investigations may run concurrently. Development uses the selected directory unless independent Git worktrees are explicitly requested. Writers in identical or overlapping canonical directories are serialized, including across Projects; sibling directories and read-only work remain independent.

The Lead's live context and structured notes include the authoritative bound repository separately from the Project materials directory. Empty Project history does not mean an empty or new repository. A repository overview is based on inspected files, not its directory name. After assigning background work, the Lead briefly acknowledges the actual running or queued action; native settlement returns its result to the same conversation for the substantive handover. That acknowledgement is not requirement completion.

The Lead records the whole human goal, constraints, completion conditions and authorized scope as a Request. Further human changes create a version of that Request; an unrelated goal remains separate. Necessary investigation, development and verification may advance within the original scope without another human message. Runtime notices cannot create a new goal or expand permission. A genuinely failed member or confirmed missing Session can be replaced explicitly with a recorded reason and exact previous assignment; the replacement has its own real identity. The failed attempt and its files remain accessible as history, while the accepted replacement becomes the current obligation.

The Project conversation header holds two entries next to the directory action, in the place and style of the native Team action. **Requests** opens an anchored panel of persistent requirements as task cards beside the one continuing Lead conversation; its badge counts the active and waiting requirements. Each card has three states: a minimal one-line strip, a rectangular progress card, and full detail. The current requirement is prominent at the top, waiting requirements retain their actual queue order, and completed requirements form a list of collapsed strips at the bottom. Every card can expand independently while current work remains visible. A newly active requirement with no assignments shows that the Lead is arranging work; an unmet or partial delivery retains its actual unresolved state.

Progress cards combine the requirement goal and Delivery with the native DSH Agent Team's task owners, actual Session activity, task dependencies and matching member reports. They show who is doing what, actual completed stage counts and waiting reasons. Full detail retains Overview, Team, Results and Activity, including the complete recorded goal, constraints and completion conditions for each revision. Historical work stays bound to its original assignment and report when the same member starts another requirement. The Requests panel holds the materials entry, queue actions and task archive/restore; **Team** opens the Project roster, member states and unassigned work in the same kind of panel. The Lead creates these records from the continuing conversation; the user does not manually create Team assignments.

Header panels open on hover after a short delay (click only when the header has collapsed them to icons), pin on click and close on Escape or an outside pointer; portaled menus inside them do not close them. Once opened, a panel keeps its cards, tabs and pages while hidden, and switching conversations resets it. Member records, results, changes and materials open in the Project dialog above the panel, so closing the dialog returns to the same panel. The earlier floating observer and its right-sidebar tab are removed; there is no window geometry to keep.

The Lead remains the one continuing conversation and coordinates development rather than editing the repository itself. A requirement can stay in discussion while another is developing. Only an accepted development instruction or an explicit enqueue action puts it into the persistent requirement queue. Within a Project, one whole requirement is active at a time; the ordered waiting requirements can be moved or cancelled through the conversation or their existing observer cards. Revising a waiting requirement preserves its place and full requirement history. Cancelled requirements retain their records in a secondary list.

Queue progress comes from the actual requirement, native member activity, waiting reasons and committed deliveries. A member becoming idle or completing a stage does not release the next requirement. Automatic handoff occurs only after the active requirement's applicable completed Delivery is durably committed and its owned work has drained. A partial handover or blocker keeps the current requirement active. Cancelling the active requirement first drains its owned work before the next one can start. Project stop, archive and cold recovery retain the queue without starting old work; explicit continuation is required. The floating observer shows the current requirement and waiting order without adding another requirement input or fabricated completion percentages.

Deliveries can embed real generative pages published by the Lead through the existing `html_render` carrier. The Host associates successful native or PTC publication events from the precise delivery turn, before its declaration, and commits their attachment references through the same durable delivery boundary. It does not accept model-invented attachment IDs or treat a generated page as proof of completion. Project reuses the existing page renderer, attachment permissions, theme and sandbox; file and execution-record actions remain native controls. Useful flow, structure and comparison explanations can be visualized without requiring a new generated page for every ordinary reply. Complete reports and technical metadata remain available on demand.

A task card can be archived from its own menu only after an applicable completed Delivery and after its active work has drained. This changes the card's presentation, not its Team work or Project lifecycle. If its delivered evidence later becomes inapplicable, that card returns to the current list as needing review, while its saved archive marker permits Restore. Project archive remains a separate sidebar row context-menu action: it drains owned work and retains the Lead conversation and materials. Notes and instructions cannot be edited until Project restoration; opening a recorded artifact still reads the current file at its original location. Whole-project status and Project archive confirmation use complete activity counts; queued work can be withdrawn individually.

Cold recovery and explicit stop retain the execution cutoff and cannot restart work on their own. A valid completed delivery still appears as delivered; this safety hold is shown as a pause only while the goal has unfinished work. A later failed delivery attempt, a real diagnostic or changed prerequisite remains visible.

Project entries use the existing sidebar’s row geometry and overflow behavior inside their separate Project category. The full canonical directory remains available on the header action. The first entry provides one short instruction above the existing composer. Task details show the actual work state and relevant result, retry or individual stop action, including current waiting reasons and failed-summary recovery. Current execution and admission states take precedence over an earlier round's pending summary. Member records and current directory changes are available from the row's detail; original directory, branch and consumed execution permissions are disclosed separately. Directory changes may include pre-existing changes and other work, rather than a task's exclusive diff. Stop-in-progress is displayed before stopped, including at the individual work level.

Project materials open from the Requests panel in the Project dialog with Results, Notes and Project instructions tabs. Results group explicit deliveries by the human goal and its version. The first layer presents the conclusion, important verification, unmet conditions and recorded files. Member reports, full evidence and earlier versions expand on demand. A result opened from progress or a task card targets that exact work, independent of the current results page. Member records opened from a report retain its exact assignment and return to the same Project result and scroll position. Entering a record subview focuses its return action; returning restores the original entry's keyboard focus when that entry is still visible. The full saved-document inventory is separate and collapsed initially.

Opening a recorded file closes the header panels so the native file or browser preview remains usable. Materials are suspended and return through the same entry with their selected result, scroll position and draft; a result, record or changes dialog gives way to the preview. Opening another Project cannot redirect the retained result or its file authority.

Recorded artifacts show their filename, recorded size and original location type. Their file-actions menu reveals the original path. Opening a file uses its exact original work and report authority; materials, report history and document entries retain that same identity. Notes prioritize the editable user text and fold generated work records. Project instructions explain their scope. Switching tabs or Projects and closing with unsaved text offers save, discard or continued editing; a failed save keeps the draft. Oversized UTF-8 input receives feedback before saving and stays editable. Archived notes and instructions remain protected and explain restoration where it affects editing.

The native Team panel defaults to current participants and recent work, with bounded pages. All records provide name/content search and separate member and work pagination. An inactive continuing member is labelled Idle. Task execution briefs expand on demand, retaining their complete original content; ordinary Teams retain their existing description previews. Member records fold assignments, peer messages and tool details. Assistant messages without visible text do not create empty headings; original records and pagination boundaries are preserved. New Project work titles and summaries describe objectives and deliverables, while execution restrictions stay in their supporting fields. Existing titles and reports are preserved.

A failed Lead summary keeps the saved results and presents a concise cause and recovery instruction. Missing credentials expose the existing native model settings; complete original diagnostics are available in a collapsed error disclosure. Project material/confirmation panels use the opaque elevated-panel token so underlying conversation text cannot show through their contents. The 0.3.6 installation assembly retains main's existing glass recipe for ordinary settings and preserves the user's global glass preference.

## Runtime contracts

- Each accepted human request has immutable delegation and native run identities. Worker reports, native completion, messages and cancellation are associated with those identities. Old completions cannot finish a new request.
- A Team task completes only after its current structured report, matching native completed settlement and owned Jobs agree. Native capacity and dependencies govern dispatch. Current prerequisite completion is checked and its exact references are frozen together before directory preparation. A prerequisite reopened during preparation returns the blocked admission to the queue.
- Reports preserve the prerequisite references actually supplied and consumed by the worker. New requests or replacement reports mark dependent results as changed; previous reports remain available, and completed downstream work does not automatically restart.
- Stop establishes an immediate source cutoff, cancels the Lead and workers and drains owned Jobs even when persistence fails. Directory occupancy remains held until actual drain. Restart and archive restoration start no model. Only a new user request permits stopped work to continue.
- Read-only and document scopes do not permit arbitrary repository writes or shell execution. Managed development commands can use native approval for one exact command and cwd. Reject, stop and late approval do not start that command or grant persistent permission. Ordinary Teams retain their existing permission behavior.
- Reading reports or producing ordinary progress replies does not deliver a Request. Explicit delivery references the exact reports and real terminal outcomes, freezes the effective required assignments, and commits only after a successful native tool result, visible final reply, completed turn and durable Session flush. Complete delivery requires every effective obligation to succeed; partial delivery retains unmet conditions. A failed summary or durable checkpoint keeps the saved results and draft. Summarize again sends an ordinary user message to the same Lead without replacing the composer draft or rerunning a worker. Recovery inspects persisted facts and starts no model or worker.
- Task cards read the persisted Request, current revision, exact Team work references and applicable Delivery. Current, completed and archived lists have separate bounded pages so unfinished work cannot be hidden behind completed pages. A card archive is allowed only for a current completed Delivery; archived evidence that becomes inapplicable is shown among current cards for review. Restore clears that Request's archive marker without resuming work.
- Detail returns at most 20 current summaries and three recent historical summaries. History, materials and report reads are paged; polling retains selected pages and rejects stale responses. Store tools consume only results actually returned, including paged historical outcomes without reports.
- Generated notes prioritize blocked and active work and have a UTF-8 byte budget. The legal user-owned suffix is preserved completely; old oversized generated content remains readable within the same budget. Preferences apply only to this Project.
- Worktree cleanup checks original ownership and runtime drain, preserves dirty and ignored files and retains branches. User directories are never reset, stashed or removed. Windows long-path support is applied to Project Git commands without changing shared Git configuration.

### Steward redesign source changes (4.2)

The source implements P1–P4 of the [steward redesign](../superpowers/specs/2026-10-15-project-steward-redesign.md). The changes are committed on `main`; they are not installed, and full real-provider and visible desktop acceptance remains incomplete. The [manual acceptance checklist](projects-steward-acceptance.md) covers what remains.

- **Project rules**: `charter.md` (16 KB) is injected into every Lead step and worker brief. Rules override the model's own defaults; an explicit user exception is confirmed once and stated. Older Projects create the file lazily. The materials editor adds a Project rules tab with common-rule toggles and a size meter; the former instructions tab is labelled Preferences.
- **Board**: plain-language status badges with a reason and next step, a whole-Project overview strip, undo on discussed or queued cards, and direct requirement creation for clear goals.
- **Deliveries**: delivered cards list their files, open them with their recorded authority, and link to changes and result pages. The diff view is split by file with line counts and colouring.
- **Requirement changes**: after workspace preparation, the first write in each actual member directory records a baseline tree through a private temporary Git index; the user's index, refs and files are untouched. Multiple members in one directory share its baseline; explicitly isolated members retain their own directory and workspace receipt. Delivery captures every end tree in the queue transaction before releasing the next requirement. The diff identifies each directory, including same-named files in different workspaces. Repository-relative file paths and workspace directory labels are shown separately, including Projects bound below a repository root. Reverts use the same cross-Project parent/child-directory exclusion as development. All directories are checked before applying any reverse patch; a conflict in this preflight changes nothing. If a later file-operation failure interrupts a multi-directory revert, completed directories are recorded immediately and the error lists completed and remaining directories; retry touches only the remaining directories. Non-Git directories have no requirement baseline.
  A failed baseline is recorded against its directory without blocking ordinary work; the host reports that missing starting point instead of offering an incomplete automatic revert or taking a new baseline after writing. Older main-only snapshots remain usable. If an older record demonstrably omitted an executed isolated member's directory, its original data is retained and the coordinator must inspect that work before reverting it.
- **Decision log**: `project_deliver` accepts a `decision`; after a durable delivery the host appends it (or the summary's first line) to `decisions.md` once, and recent entries are injected into the Lead. Reverts are logged.
- **Queued preparation**: an authorized queued requirement may run read-only investigation; docs and development still wait for activation, and discussed or cancelled requirements cannot run. The Lead's open human turn is queried through `humanTurnOpen()`. No Agent Teams source change is required: system prompt sections are re-rendered every step and compaction keeps the system head.
- Deferred: automatic cross-requirement worktree parallelism and the architecture map, for the reasons recorded in the design.
